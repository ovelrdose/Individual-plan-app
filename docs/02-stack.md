# Этап 2. Выбор стека технологий

Статус: **согласовано** (уточнено: MS Excel — основной инструмент печати)

## 1. Что определяет выбор

| Фактор | Значение для стека |
|---|---|
| До 50 одновременных пользователей, одна клиника | Высокая нагрузка не нужна. Хватит одного сервера и монолита без микросервисов, очередей и кэш-кластеров |
| Свой сервер в сети клиники, сопровождение на Python | Только Python на бэкенде. Минимум отдельных сервисов, которые надо обслуживать. Простой деплой и бэкап |
| Основная ценность — данные и правила: справочники, назначения, бронирования, ограничения | Нужны реляционная БД с ограничениями целостности и хорошая ORM |
| Много справочников (группы, тренажёры, инструкторы, процедуры, смены, отделения) | Готовая админка экономит недели работы |
| Простая система пользователей и ролей | Готовая аутентификация и права «из коробки» |
| Работа с Excel и Word: импорт docx и xlsx, экспорт карты по шаблону | Зрелые Python-библиотеки: openpyxl, python-docx |
| Главный экран — сетка расписания с ручной правкой | Нужна интерактивность (клик по ячейке, выбор, подсветка конфликтов), но не полноценное SPA |
| Персональные данные (152-ФЗ) | Аутентификация, журнал изменений, работа без внешних CDN и облачных сервисов |
| Сервер внутри сети, интернета может не быть | Все JS- и CSS-библиотеки лежат в проекте, сборка фронтенда на сервере не нужна |

## 2. Рассмотренные варианты

### Вариант A — Django + HTMX (серверный рендеринг) — **рекомендую**
Django 5.2 LTS, PostgreSQL, шаблоны Django, HTMX и Alpine.js для интерактивности.

- **Плюсы:**
  - есть админка для справочников, аутентификация, группы и права, миграции, формы с валидацией, защита от CSRF и XSS;
  - один язык и один репозиторий, фронтенд не нужно собирать;
  - HTMX обновляет фрагменты страницы (ячейку сетки, панель конфликтов) без перезагрузки — для сетки расписания этого достаточно;
  - у Django жёсткие соглашения о структуре — такой код легко сопровождать одному разработчику (и вместе с Claude);
  - LTS-ветка поддерживается до апреля 2028.
- **Минусы:** сложное drag-and-drop-редактирование сетки труднее, чем в React. Решаем точечно небольшими JS-компонентами (SortableJS и Alpine.js) только на экране сетки.
- **Трудоёмкость:** базовая (1×).

### Вариант B — FastAPI + React (SPA)
FastAPI, SQLAlchemy и Alembic, PostgreSQL, React + TypeScript + Vite.

- **Плюсы:** максимально гибкий и «живой» интерфейс, чёткое разделение API и UI.
- **Минусы:**
  - админку, аутентификацию, права и формы придётся писать самим или собирать из библиотек;
  - два языка и два стека, нужна сборка фронтенда;
  - сопровождать сложнее, особенно если разработчик один и пишет на Python.
- **Трудоёмкость:** примерно 1,7–2×.

### Вариант C — Django REST Framework + Vue/React
Гибрид A и B: админка и права Django, интерфейс — SPA.

- **Плюсы:** админка Django плюс богатый UI.
- **Минусы:** всё равно два стека и сборка фронтенда. Каждый экран делается дважды: API + компонент.
- **Трудоёмкость:** примерно 1,5×.

### Почему не «остаться в Excel» (макросы или Google Таблицы)
Excel не даёт многопользовательской работы с блокировками, ролей, журнала изменений и общей шахматки на несколько отделений. Google Таблицы не подходят из-за 152-ФЗ и работы во внутренней сети.

## 3. Рекомендуемый стек (вариант A)

| Слой | Технология | Зачем |
|---|---|---|
| Язык | Python 3.12+ | Требование сопровождения; на нём же все библиотеки для работы с файлами |
| Веб-фреймворк | Django 5.2 LTS | Админка, аутентификация, права, ORM, миграции, формы |
| БД | PostgreSQL 16+ | Целостность данных, транзакции. **`ExclusionConstraint` + `btree_gist`** на уровне БД не дают записать к одному инструктору два пересекающихся по времени занятия, даже если два специалиста сохраняют одновременно |
| Интерфейс | Шаблоны Django + HTMX 2 + Alpine.js 3 | Интерактивность без SPA и без сборки |
| Сетка расписания | HTMX + Alpine.js, SortableJS при необходимости drag-and-drop | Ручная правка, подсветка конфликтов |
| CSS | Bootstrap 5 (локальные файлы) | Готовые таблицы, формы, модальные окна; без сборки |
| Импорт Excel / экспорт карты | openpyxl | Чтение `lfk.xlsx`, `basseyn.xlsx`, шахматки; заполнение `programm_template.xlsx` с сохранением логотипов и форматирования |
| Импорт листа назначений | python-docx | Разбор шапки и таблицы «Физиотерапия» |
| Печать | **MS Excel на рабочих местах** (основной редактор таблиц в организации) | Пользователь скачивает xlsx и печатает из Excel. Параметры страницы, область печати и масштаб берутся из шаблона |
| PDF (опционально) | LibreOffice в режиме без интерфейса (xlsx → pdf) | Только как дополнительная кнопка «скачать PDF». Основной путь печати — MS Excel |
| Движок подбора | Чистый Python (жадная эвристика со скорингом) | Просто и объяснимо, легко тестируется. Интерфейс движка позволит позже подключить OR-Tools (CP-SAT) |
| Журнал изменений | django-simple-history | История каждой записи: кто, когда, что изменил (152-ФЗ, разбор ошибок) |
| Фоновые задачи | Не нужны на старте | Импорт и подбор укладываются в секунды. Если понадобятся — django-q2 или Celery позже |
| Тесты | pytest, pytest-django, factory_boy | Обязательное покрытие движка подбора, импорта и экспорта |
| Качество кода | ruff (линтер и форматтер), mypy (по желанию) | Единый стиль |
| Зависимости | `pyproject.toml` (`[dependency-groups]`), точные версии `==`, установка `pip install --group dev` в `.venv` | Воспроизводимые сборки без дополнительных инструментов |
| Запуск в проде | Docker Compose: nginx + gunicorn + PostgreSQL | Один сервер, одна команда для обновления |
| Бэкап | `pg_dump` по расписанию + копия на другой диск или сервер | Восстановление данных |
| Разработка | Docker Compose (PostgreSQL) + `runserver`; django-debug-toolbar | Та же СУБД, что и в проде: ограничения PostgreSQL работают и при разработке |

## 4. Совместимость с MS Excel

MS Excel — основной редактор таблиц в организации. Согласовано: **все правки вносятся в веб-системе, а Excel нужен для печати** (и мелких разовых правок перед печатью, которые в систему не возвращаются). Отсюда требования к выгрузке:
- Файлы `.xlsx` должны без предупреждений открываться в MS Excel. Проверка на реальной версии Excel в клинике входит в приёмку.
- Даты и время записываются **настоящими значениями Excel** с форматом `ДД.ММ` и `Ч:ММ`, а не числами вида `2.1` или `9.4`, как сейчас в шаблоне.
- Из шаблона сохраняются логотипы, объединённые ячейки, шрифты, рамки, область печати, ориентация и масштаб «вписать в страницу». Риск: openpyxl может потерять часть графических объектов шаблона — проверяем на прототипе. Запасной путь — добавлять логотипы программно.
- Шахматка дня выгружается в привычной раскладке: инструкторы × слоты, справа таблица тренажёров.
- Импорт `.xlsx` (справочники, текущая шахматка) рассчитан на файлы, сохранённые в MS Excel.

## 5. Требования к серверу (ориентир)
- 2–4 vCPU, 4–8 ГБ RAM, 50 ГБ SSD. Этого хватает с запасом на 50 пользователей, PostgreSQL и LibreOffice.
- Linux (Ubuntu Server LTS / Debian), Docker, Docker Compose.
- HTTPS внутри сети (сертификат клиники или самоподписанный).
- Доступ в интернет для работы не нужен, нужен только для установки обновлений.

## 6. Риски выбора и что с ними делать

| Риск | Что делаем |
|---|---|
| На HTMX неудобно строить сложную сетку | Сетку проектируем на этапе 3 отдельно. Если HTMX и Alpine.js не хватит — только на этом экране встраиваем небольшой изолированный JS-компонент, без перехода на SPA |
| Выгруженный xlsx в MS Excel выглядит или печатается не так, как шаблон | Проверяем на прототипе первым делом, на реальном Excel клиники. Шаблон хранится в системе, и администратор может его заменить |
| LibreOffice искажает шаблон при конвертации в PDF | PDF — дополнительная функция. Основная печать идёт из MS Excel |
| Жадный алгоритм даёт неоптимальное распределение | Метрики равномерности в отчёте. Специалист правит вручную. При необходимости — CP-SAT за тем же интерфейсом |
| Один разработчик на сопровождении | Стандартная структура Django, тесты, `CLAUDE.md`, документация в `docs/` |
