## 1. Общая схема

```
 Рабочие места (браузер + MS Excel для печати)
        │  HTTPS (внутренняя сеть)
        ▼
 ┌──────────────── Сервер клиники (Docker Compose) ────────────────┐
 │  nginx ── статика, загрузка файлов, HTTPS                         │
 │    │                                                              │
 │  gunicorn ── Django-приложение (модульный монолит)                │
 │    │            ├─ веб-интерфейс (шаблоны + HTMX)                 │
 │    │            ├─ админка (справочники)                          │
 │    │            └─ импорт и экспорт (docx, xlsx, pdf*)             │
 │    │                                                              │
 │  PostgreSQL ── все данные (единственный источник истины)          │
 │  LibreOffice* ── конвертация xlsx → pdf (опционально)             │
 │  cron ── pg_dump бэкап                                            │
 └───────────────────────────────────────────────────────────────────┘
```

Внешних интеграций нет. Файлы `.docx` и `.xlsx` пользователь загружает через браузер. Выгруженные `.xlsx` скачивает, открывает в MS Excel и печатает.

## 2. Слои

```
 ┌──────────────────────────────────────────────────────────────┐
 │ Представление: views, шаблоны, формы, HTMX-фрагменты, админка │  только ввод/вывод, права
 ├──────────────────────────────────────────────────────────────┤
 │ Сервисы приложения (services.py): сценарии использования,     │  транзакции, блокировки,
 │ «завести госпитализацию», «подобрать расписание»,             │  вызов домена, запись в БД
 │ «переместить занятие», «выгрузить карту»                      │
 ├──────────────────────────────────────────────────────────────┤
 │ Домен (domain/): чистый Python без Django —                   │  правила, движок подбора,
 │ интервалы, правила ограничений, движок подбора, разбор        │  парсеры; 100% unit-тесты
 │ текста назначений, расчёт дат курса                           │
 ├──────────────────────────────────────────────────────────────┤
 │ Инфраструктура: модели ORM, адаптеры файлов                   │  PostgreSQL, openpyxl,
 │ (docx-ридер, xlsx-ридер, xlsx-писатель по шаблону, pdf)       │  python-docx, LibreOffice
 └──────────────────────────────────────────────────────────────┘
```

Правила:
- Views не содержат бизнес-логики, они только вызывают сервисы.
- Домен не импортирует Django: на вход получает dataclass-снимки данных, на выход отдаёт предложения (план бронирований и список конфликтов). Поэтому движок можно тестировать и заменять независимо от остального кода.
- Запись в БД идёт только через сервисы, внутри транзакции.

## 4. Модель данных

### 4.1. Организация и пользователи
- **Department** — отделение: `name` («ОМР № 4»), `code`, `course_days` (JSON `{3: 11, 4: 15, 5: 20}`), `max_individual_per_day` (2), `is_active`.
- **User** — стандартный пользователь Django.
- **Membership** — `user`, `department`, `role` (врач / специалист ФР). У пользователя может быть несколько отделений. Администратор — флаг `is_superuser` или группа «Администратор».

### 4.2. Справочники (catalog)
- **Procedure** — процедура из назначения:
  - `name`, `card_label` (как пишется в карте), `synonyms` (массив: «ST – 150», «st-150», «st»);
  - `kind`: `LFK_GROUP` | `POOL` | `INDIVIDUAL` | `EQUIPMENT` | `CARD_ONLY`;
  - `default_duration_min`, `place` («эргозона», «зал ЛФК», «бассейн»);
  - `equipment` (для `EQUIPMENT`), `department` (null — общая для центра).
- **GroupSession** — ежедневное повторяющееся занятие: `procedure` (ЛФК-группа или группа бассейна), `start_time`, `duration_min`, `place`. Одна процедура может иметь несколько сессий в день (Нейро-тренинг 10:30 и 14:20). Ёмкость не ограничена.
- **Бассейн:** процедуры вида `POOL` — «ЛФК в воде: верхняя конечность», «…нижняя», «…спина»; у каждой свои `GroupSession`. Назначение «бассейн» без указания группы ссылается на общую процедуру «Бассейн», и тогда специалист ФР выбирает конкретную группу.
- **Equipment** — тренажёр: `name` (st-150, Имитрон, Pablo), `window_start` (13:00), `window_end` (15:00), `step_min` (15), `capacity` (настраивается), `duration_min`.
- **InstructorSlotGrid** — сетка слотов инструкторов: список `(start, end)`, т. е. 9:10–9:40 … 16:20–16:50 и вечерние слоты. Одна сетка на центр, её можно редактировать.

### 4.3. Персонал (staff)
Всё о сменах и распорядке инструкторов живёт в `apps/staff` (шаг 3.1); у каждой модели — журнал (`HistoricalRecords`), ссылки — `PROTECT`.
- **Instructor** — `full_name`, `short_name` («Атаманчук»), `partner` (напарник по 2/2, связь симметрична — `services.set_partner`), `display_order`, `is_active`.
- **ShiftPattern** — `instructor`, `pattern` (`2/2`, `5/2`, `daily`), `anchor_date` (первый рабочий день цикла), `valid_from`, `valid_to` (пусто — бессрочно). Периоды одного инструктора не пересекаются: `ExclusionConstraint` (`instructor =`, `daterange(valid_from, valid_to, '[]') &&`). Смена шаблона «с даты» закрывает прежний накануне (`services.change_shift_pattern`).
- **ShiftException** — `instructor`, `date`, `is_working`, `reason` (отпуск, больничный, подмена); уникально `(instructor, date)`. Хранится только отступление от шаблона: отметка, совпавшая с шаблоном, удаляет исключение (`services.set_working`).
- **InstructorDuty** — постоянный распорядок (TZ.md, FR-STF-5): `instructor`, `slot` (→ `catalog.InstructorSlot`), `kind` (`METHOD_WORK` / `GROUP_LEAD` / `BOS` / `OTHER`), `group_session` (→ `catalog.GroupSession`, только для `GROUP_LEAD`, занятие должно попадать в слот), `label` (для `OTHER`), `valid_from`, `valid_to`. Действует в рабочие дни инструктора. Одна обязанность в слоте на пересекающийся период — `ExclusionConstraint` (`instructor =`, `slot =`, период `&&`).
- **InstructorBlock** — разовое изменение на дату: `instructor`, `date`, `slot`, `kind` (те же + `CLEAR` — «снять распорядок в этот день»), `group_session`, `label`; уникально `(instructor, date, slot)`.
- **Ведение группы** занимает все слоты, с которыми пересекается его занятие группы (не только выбранный); разовый блок в любом из них снимает ведение целиком.
- **Домен** `apps/staff/domain.py` (без Django): `is_working(patterns, exceptions, day)`, `busy_slots(duties, blocks, day, working)` и `InstructorCalendar` — «работает ли в дату» и «чем занят каждый слот» (`InstructorDay.is_free(slot_id)`, `busy[slot_id].text`). Исключение важнее шаблона, разовый блок важнее распорядка, `CLEAR` освобождает слот. Данные для домена собирает `services.instructor_calendars(instructors, start, end)` — им пользуются подбор индивидуальных и шахматка. Календарь помнит загруженный диапазон дат и на дату вне него отвечает `ValueError`. Команды шахматки (одиночка или пара 2/2) — `domain.Team` (`key`, `label` «А/ Б»), строит `services.build_teams()`; `domain.team_candidates(team, calendars, day, slot_id)` — кто из команды работает и свободен в слоте.

### 4.4. Пациенты (patients)
- **Admission** (госпитализация) — `department`, `full_name`, `sex`, `age`, `history_number` (ИБ), `room` («9», «5а»), `shrm` (3/4/5), `diagnosis`, `attending_doctor` (FK User / ФИО врача), `admission_date`, `discharge_date` (вычисляется по ШРМ, редактируется), `status` (черновик / активен / выписан).
- **Prescription** — `admission`, `procedure` (может быть пустой, если строка не распознана), `raw_text` (исходная строка из docx), `duration_min`, `per_day`, `start_date`, `cancel_date`, `pool_procedure_hint`, `in_card` (выводить ли в нижний блок), `card_order`.

### 4.5. Расписание (scheduling)
- **Booking** — занятие пациента в конкретную дату:
  - `admission`, `date`, `start`, `end`, `procedure`;
  - `kind`: `LFK_GROUP` | `POOL` | `INDIVIDUAL` | `EQUIPMENT`;
  - `group_session` (для групп), `instructor` + `slot` (→ `catalog.InstructorSlot`, для индивидуальных; время занятия = время слота), `equipment` (для тренажёров);
  - `note` (art, Мото-Л, шар), `source` (`auto` / `manual` / `import`), `pinned` (ручное, движок его не трогает), `version` (оптимистическая блокировка).
- **InstructorDuty** и **InstructorBlock** (постоянный распорядок и разовые блоки, TZ.md, FR-STF-5) — модели `apps/staff`, см. §4.3. Расписание видит их через `staff.services.instructor_calendars` как занятые слоты.
- **Program.preferred_instructor** — инструктор по желанию пациента (TZ.md, решение 44): FK `staff.Instructor`, `PROTECT`, пусто — не задан; в журнале программы. Задаёт специалист ФР в блоке «Расписание» (`scheduling.services.choose_preferred_instructor`).
- **Подбор индивидуальных** (шаг 3 движка) — в `replan` вместе с группами и тренажёрами (решение 50). Вход движка — `domain.Staff`: дневные слоты, команды (`staff.domain.Team`), тройки «дата × слот × инструктор свободен» (смены, распорядок, блоки, индивидуальные других программ всех отделений), загрузка инструкторов за даты курса, `preferred`, `previous` (прошлые автоматические постановки, решение 49). Порядок блокировок в `replan`: программа → тренажёры → инструкторы (`select_for_update`, по pk).
- **Ограничения целостности в БД:**
  1. Один инструктор — одно занятие в слоте: частичный уникальный индекс `(instructor, date, slot)` на `Booking` (индивидуальные, `booking_instructor_slot_unique`); `CheckConstraint` `booking_instructor_only_individual` — инструктор и слот заполнены ровно у индивидуальных. При сохранении сервис проверяет также распорядок и `InstructorBlock`, используя блокировку строк инструкторов.
  2. Пациент не может быть в двух местах сразу: `ExclusionConstraint` на `Booking` по `(admission =, tsrange(date+start, date+end) &&)`.
  3. Вместимость тренажёра (> 1): сервис блокирует строку `Equipment` (`SELECT … FOR UPDATE`) и считает занятость в слоте.

### 4.6. Карты (cards)
- **CardTemplate** — `department`, `shrm`, `file` (xlsx), `mapping` (JSON: какие ячейки или диапазоны за что отвечают — шапка, блок «Расписание занятий», строки процедур, строка дат, второй блок дат для ШРМ5).
- Карта не хранится как файл — она всегда генерируется из актуальных данных. Журнал выгрузок: кто и когда выгрузил, для какой госпитализации.

### 4.7. Схема связей (упрощённо)

```
Department 1─* Admission 1─* Prescription *─1 Procedure *─0..1 Equipment
                    │                              │
                    1                              1─* GroupSession
                    *                              │
                 Booking *──────────────────────────┘
                    │ *─0..1 Instructor 1─* ShiftPattern / ShiftException
                    │ *─0..1 Equipment          │
                    │ *─0..1 GroupSession        └─ partner (Instructor)
Instructor 1─* InstructorDuty *─1 InstructorSlot,  InstructorDuty *─0..1 GroupSession
Instructor 1─* InstructorBlock *─1 InstructorSlot, InstructorBlock *─0..1 GroupSession
Department 1─* CardTemplate,  User *─* Department (Membership: role)
```

## 5. Движок подбора расписания

### 5.1. Вход и выход
- **Вход (снимок):** госпитализация с датами курса и назначениями, расписание групп, сетка слотов, инструкторы с графиком смен, все существующие бронирования и блоки за период (**все отделения**), настройки отделения.
- **Выход:** список предлагаемых `Booking` + список конфликтов и предупреждений. В БД ничего не пишется, пока специалист не нажмёт «Применить».

### 5.2. Ограничения
**Жёсткие** (нарушать нельзя):
- пациент не находится в двух местах одновременно (по реальным интервалам, а не по слотам);
- инструктор в смене в эту дату, слот свободен и не заблокирован;
- индивидуальных занятий не больше, чем назначено, и не больше лимита отделения (2);
- тренажёры только в окне тренажёра (13:00–15:00), с шагом и в пределах вместимости;
- даты — только внутри курса и периода действия назначения.

**Мягкие** (оптимизируются):
- одно и то же время занятий каждый день курса (карта печатает одно расписание);
- за пациентом закреплена пара напарников 2/2;
- равномерная загрузка инструкторов за период;
- два индивидуальных занятия в день не идут подряд (по возможности).

### 5.3. Алгоритм (вариант A — жадный, рекомендован)
1. **Даты курса:** `admission_date … admission_date + course_days[shrm] − 1`.
2. **Группы ЛФК:** для каждой назначенной группы берётся её сессия. Если сессий несколько — выбирается та, что не пересекается с уже поставленными. Если без пересечения поставить нельзя — это конфликт, решение за специалистом.
3. **Бассейн:** группа из назначения (или выбранная специалистом) → её сессия без пересечений.
4. **Индивидуальные:** для каждой требуемой ежедневной единицы (1 или 2):
   - кандидаты — пары `(инструктор или пара напарников, слот)`;
   - для каждого кандидата и каждой даты курса проверяется: кто из пары в смене, свободен ли слот, свободен ли пациент;
   - **скоринг:** доля дат курса, на которые кандидат проходит (главное), + суммарная загрузка пары за период (меньше — лучше) + штраф за соседство со вторым индивидуальным занятием;
   - выбирается лучший кандидат. На даты, где он не проходит, подбирается замена на конкретный день (другой инструктор, тот же или ближайший слот). Такие даты помечаются предупреждением.
5. **Тренажёры:** для каждого назначенного тренажёра — шаг в окне 13:00–15:00 со свободной вместимостью, без пересечений с занятиями пациента. Предпочтение — одно и то же время каждый день.
6. **Отчёт:** что поставлено, что не удалось, где расписание отличается по дням, как изменилась загрузка инструкторов.

Обработка идёт **инкрементально**: подбор делается для одного нового пациента, существующие бронирования не двигаются. Закреплённые (`pinned`) и ручные бронирования движок никогда не меняет. Операция «Перебалансировать» (по желанию, этап 2+) пересчитывает только незакреплённые будущие бронирования.

### 5.4. Вариант B — оптимизатор OR-Tools CP-SAT
Глобальная оптимизация по всем пациентам сразу. Даёт лучшее распределение, но сложнее в отладке и хуже объясняет пользователю, «почему так». Подключается за тем же интерфейсом `ScheduleEngine.propose(snapshot) -> Proposal`, если жадного алгоритма не хватит.

## 6. Ключевые сценарии и взаимодействие компонентов

### 6.1. Заведение пациента
```
Врач → [Новая госпитализация] → форма (ФИО, пол, возраст, ИБ, ШРМ, палата, диагноз, дата поступления)
   или → [Загрузить docx] → exchange.DocxPrescriptionReader → domain.parse_prescriptions(текст)
        → сопоставление с Procedure.synonyms → экран подтверждения
          (распознано ✓ / нужно выбрать ✗ / не для расписания → «только в карту»)
→ patients.services.create_admission() → Admission + Prescription[]
```

### 6.2. Подбор расписания
```
Специалист ФР → карточка пациента → [Подобрать]
→ scheduling.services.propose(admission)
     собирает снимок → domain.engine.propose() → Proposal
→ экран-предпросмотр: «типичный день» + календарь курса, конфликты подсвечены
→ правки (сменить группу, слот, инструктора) — каждая проверяется на лету (HTMX)
→ [Применить] → транзакция: блокировки → повторная проверка → запись Booking
   (если за это время слот занял кто-то другой → понятная ошибка + повторный подбор)
```

### 6.3. Ручная правка (в любой момент)
- В карточке пациента: перенести, удалить, добавить занятие на одну дату или «на все оставшиеся даты».
- В шахматке дня (специалист ФР): клик по ячейке → выбрать пациента, блок («Метод. работа», группа, БОС), перенести или очистить; «закрепить пациента за инструктором».
- Инструктор заболел или не вышел → его занятия на эти даты перестраиваются автоматически, специалист видит сводку (TZ.md, FR-SCH-13).
- Любая правка проходит те же проверки ограничений, правка от руки становится `pinned`.

### 6.4. Изменения курса
- Отмена назначения или досрочная выписка → будущие бронирования удаляются, слоты освобождаются.
- Продление → предложение подобрать на новые даты.
- Изменение смены инструктора (больничный) → список затронутых бронирований → «Подобрать замену».

### 6.5. Печать карты
```
[Скачать карту .xlsx] → cards.services.build_card(admission)
→ выбор CardTemplate(department, shrm) → openpyxl: копия шаблона,
   заполнение по mapping: шапка, «Расписание занятий» (типичный день: время | процедура | место),
   нижний блок: строки процедур (in_card) × даты курса (настоящие даты Excel)
→ файл → браузер → MS Excel → печать
```
Если расписание в разные дни отличается, в верхний блок идёт наиболее частый вариант, а отличия выводятся предупреждением перед выгрузкой.

### 6.6. Шахматка
- Экран «Шахматка на дату»: инструкторы в смене × слоты, справа тренажёры. Видны пациенты **всех отделений** с пометкой отделения («16п ОМР 1 Мазолова»).
- Выгрузка в `.xlsx` в привычной раскладке для печати и переходного периода.

## 7. Мультиотделения

- Пациенты, назначения, карты и шаблоны карт принадлежат **отделению**. Пользователь видит пациентов только тех отделений, в которых состоит.
- Инструкторы, тренажёры, бассейн, сетка слотов и шахматка — **ресурсы центра**. Движок подбора всегда учитывает занятость по всем отделениям.
- В шахматке и в сетке ресурса чужие пациенты видны в объёме «палата, фамилия, отделение» — этого достаточно, чтобы не было двойной записи, и это минимум персональных данных.
- Новое отделение добавляется через админку: создать `Department`, задать настройки, загрузить шаблоны карт, назначить пользователей. Код при этом не меняется.

| Подбор и правка расписания пациента | ✓ | просмотр | ✓ | — |

| Шахматка: поставить или убрать пациента | ✓ | просмотр | ✓ | — |
| Шахматка: блоки, смены | ✓ | — | ✓ | — |
| Шахматка: просмотр | ✓ | ✓ | ✓ | ✓ (`/board/`; на проде только из сетей клиники) |

Роли «инструктор» и «просмотр» убраны (TZ §13, п. 4). Все сотрудники отделения видят все его программы (TZ §13, п. 37).

Права проверяются в сервисах (а не только в шаблонах): роль + членство в отделении.

## 9. Экраны

1. **Вход.**
2. **Пациенты отделения** — список активных: ФИО, палата, ШРМ, даты, статус расписания (не подобрано / подобрано / есть конфликты). Переключатель отделения.
3. **Госпитализация** — данные пациента, назначения (таблица с выбором из справочника), импорт docx.
4. **Расписание пациента** — «типичный день» (как верхний блок карты) + календарь курса по датам. Кнопки «Подобрать», «Применить», «Скачать карту».
5. **Шахматка на дату** — сетка инструкторов и тренажёров с правкой ячеек, переход между датами.
6. **Смены инструкторов** — календарь месяца (как `Лист3`), исключения.
7. **Загрузка инструкторов** — отчёт за период: сколько индивидуальных занятий у каждого (контроль равномерности).
8. **Справочники** — админка Django: процедуры, группы, бассейн, тренажёры, сетка слотов, шаблоны карт.
9. **Импорт** — справочники и текущая шахматка из xlsx с отчётом о нераспознанном.
10. **История изменений** записи.

## 10. Импорт и экспорт

| Операция | Адаптер | Особенности |
|---|---|---|
| Импорт листа назначений `.docx` | `DocxPrescriptionReader` | Шапка разбирается регулярными выражениями (ФИО, ИБ, ШРМ, диагноз, палата). Колонка «Физиотерапия» делится на строки, строки «Групповые занятия ЛФК — A — B» раскрываются в несколько назначений. Длительность и частота извлекаются по шаблону `\d+ мин`, `\d+ р/д`. Всё остальное сопоставляется по синонимам, неуверенные совпадения подтверждает человек |
| Импорт справочников `lfk.xlsx`, `basseyn.xlsx` | `XlsxCatalogReader` | Время как доля суток → `time`. Просмотр перед сохранением |
| Импорт текущей шахматки (разово) | `XlsxDayBoardReader` | Один лист → дата. Колонки → инструкторы (вида «A/ B» → пара). Ячейки → «Nп [ОМР X] Фамилия [пометка]» → поиск госпитализации по палате и фамилии. Нераспознанное попадает в отчёт |
| Экспорт карты `.xlsx` | `XlsxCardWriter` | По `CardTemplate.mapping`. Даты и время — настоящие значения Excel. Параметры печати шаблона сохраняются |
| Экспорт шахматки `.xlsx` | `XlsxDayBoardWriter` | Привычная раскладка |
| PDF (опционально) | `PdfConverter` | LibreOffice в режиме без интерфейса |

## 11. Надёжность, безопасность, эксплуатация

- **Конкурентный доступ:** транзакции, ограничения БД (§4.5), блокировка строк ресурса при записи, поле `version` у `Booking` для оптимистической блокировки при ручной правке.
- **Безопасность:** вход по логину и паролю (политика паролей Django), сессии с таймаутом, HTTPS, CSRF, права по ролям и отделениям, никаких внешних CDN.
- **Журнал:** история изменений по госпитализациям, назначениям, бронированиям, блокам и сменам (кто, когда, было → стало). Журнал выгрузок карт.
- **Бэкап:** ежедневный `pg_dump` с ротацией и копией на другой носитель, инструкция по восстановлению.
- **Логи:** логи приложения в файл или journald; ошибки 500 — с трассировкой в лог.
- **Обновление:** `git pull` → `docker compose up -d --build` → миграции.
